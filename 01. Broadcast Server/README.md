# Broadcast Server (client-side relay)

간단한 브로드캐스트 중계기(클라이언트)입니다. 여러 upstream WebSocket 서버에 연결하여 수신된 메시지를 콜백으로 전달하거나 로컬 로그로 저장할 수 있습니다.

용도: 이후 프론트엔드(`Pinia`)로 전달할 중계기 역할을 구현할 때, 이 프로그램을 확장하여 HTTP/WebSocket으로 프론트엔드에 푸시할 수 있습니다.

실행 예시:

```bash
cd "01. Broadcast Server"
python3 -m pip install -r requirements.txt
python3 broadcast_manager.py --uri ws://127.0.0.1:8080
```

구현 요약:
- `Connection` 클래스: 단일 upstream WebSocket 연결 담당(자동 재연결, 메시지 수신)
- `BroadcastManager` 클래스: 여러 `Connection`을 리스트로 관리, 전역 콜백 등록 기능

확장 포인트:
- 콜백을 통해 Pinia로 전달할 중간 API(예: WebSocket 서버 또는 HTTP 엔드포인트)로 포워딩
- 메시지 필터링/변환 레이어

🔍 핵심 컴포넌트 상세 설명
1. 로봇과의 소통을 전담하는 UpstreamConnection
이 클래스는 시스템 내부에서 로봇 한 대당 하나씩 생성되는 독방입니다.

주요 역할: 지정된 로봇 IP에 웹소켓 클라이언트로 접속하고, 연결이 끊기면 3초마다 좀비처럼 다시 연결을 시도(connect_loop)합니다.

핸드셰이크 자동화: 로봇이 보안이나 세션 검증을 위해 접속 직후 특정 패킷을 요구하면, 여기에 메시지 ID와 타임스탬프를 실시간으로 구워서 자동으로 던져줍니다.

출구: 로봇이 데이터를 던져주면, 본인이 직접 처리하지 않고 등록된 콜백 함수(on_message_cb)를 호출해 데이터를 상위 파이프라인으로 넘겨버립니다.

2. 데이터 유효성 검사 및 네비게이션 MessageParser
날것의 데이터가 들어왔을 때 가장 먼저 거치는 정제소입니다. 인스턴스를 만들지 않는 정적 클래스(@staticmethod)로 설계되어 가볍고 빠르게 동작합니다.

정규화: 로봇마다 데이터 포맷이 미세하게 다를 수 있으므로, 시스템 공통 포맷(source, timestamp, payload)으로 모양을 통일합니다.

라우팅(분기) 판단: 내용물을 까보고 "에러"나 "비상(is_emergency)"이라는 키워드가 있으면 target_channel = "events"라는 태그를 붙이고, 평상시 상태 데이터면 "telemetry"라는 태그를 붙여서 돌려줍니다.

3. 웹 클라이언트(Vue.js) 관방 DownstreamChannelBroker
이 클래스는 중계기 서버가 웹소켓 서버 역할을 하기 위해 필요합니다. URL 엔드포인트 개수만큼 인스턴스가 생성됩니다. (현재 코드에서는 Telemetry용, Events용 총 2개)

커넥션 세션 관리: 현재 이 채널에 접속 중인 웹 브라우저(Vue app)들의 소켓 세션을 Set 배열에 모아서 쥐고 있습니다.

브로드캐스트: 파이프라인으로부터 데이터가 넘어오면, 쥐고 있는 모든 웹 클라이언트 세션에 for 문을 돌려 동시에 데이터를 흩뿌립니다. 전송하다가 브라우저가 닫혀서 에러가 난 세션은 그 즉시 명단에서 지워버립니다(disconnect).

4. 전체 시스템의 지휘관 BroadcastManager
이 모든 방을 개설하고 가동하는 총괄 매니저입니다.

servers.json을 읽어서 로봇 개수만큼 UpstreamConnection을 만들고 가동시킵니다.

가장 중요한 pipeline_process 메서드를 가지고 있습니다. 로봇이 보낸 데이터가 UpstreamConnection ➡️ MessageParser를 거쳐 가공되면, 태그를 확인하고 알맞은 DownstreamChannelBroker로 쏘아주는 실시간 데이터 스위칭 역할을 합니다.

🔄 실시간 데이터 흐름 (Data Lifecycle)
예를 들어 "Robot_Alpha"가 "배터리 부족 에러" 패킷을 던졌을 때 데이터가 흐르는 가상 시나리오입니다.

수집: UpstreamConnection[Robot_Alpha] 내부의 async for raw_msg in ws: 루프가 로봇이 보낸 문자열을 감지합니다.

이동 1: 소켓 방은 이 문자열을 가지고 manager.pipeline_process()를 호출합니다.

정제 및 분류: MessageParser.parse_and_route()가 작동합니다. 내용물에 'error'가 포함되어 있으므로 결과 가공 프레임에 target_channel: "events"라는 주소 라벨을 붙여 반환합니다.

스위칭: BroadcastManager가 라벨을 확인하고 self.events_broker.broadcast()를 호출합니다. (이때 Telemetry 브로커는 완전히 침묵하므로 자원이 낭비되지 않습니다.)

도착: events_broker가 현재 ws://localhost:8000/ws/robots/events 주소에 꼽혀 있는 Vue.js의 useAlertStore로 데이터를 전송합니다. 화면 상단에 비상 경고 팝업이 뜹니다.

🎯 이 구조가 유지보수에 좋은 이유 (결론)
로봇이 추가되거나 IP가 바뀌면? ➡️ 파이썬 코드를 건드릴 필요 없이 servers.json만 수정하면 끝납니다.

새로운 종류의 로봇 패킷(예: 카메라 영상 메타데이터) 채널을 늘리고 싶다면? ➡️ MessageParser에 조건문 하나 추가하고, FastAPI 라우터에 주소(@app.websocket("/ws/robots/videos")) 하나만 새로 파주면 기존 코드의 오작동 없이 안전하게 확장됩니다.

Vue.js 화면 개발자는? ➡️ 복잡한 로봇들의 IP나 핸드셰이크는 신경 쓸 필요 없이, 중계기가 열어준 정제된 단 2개의 주소만 구독하면 되므로 프론트엔드 코드 오버헤드가 극적으로 줄어듭니다.
